# ResNet18 initial baseline — user-supplied terminal transcript (2026-11-03)

These values are **transcribed from the user's last ResNet18 run in the chat**,
not generated by `benchmark_repro.py`, GPU CI, or independent verification.

- GPU context: RTX 5080 from the ongoing test workflow; the transcript itself
  does not include a driver/PyTorch/Triton version snapshot.
- Network: random-weight `resnet18(weights=None)`, FP16, 224×224, eval/inference mode.
- Input batch sizes 1, 8, 32. Eager, torch.compile default and reduce-overhead.
- The baseline came from the exploratory benchmark with CUDA events; unlike
  `benchmark_repro.py`, it did **not** measure across shuffled repeated rounds.
- Allclose evaluated with rtol=0.01 and atol=0.01.
- Full transcribed scalar results: [baseline_2026-11-03.csv](baseline_2026-11-03.csv).

## Key observations

| Batch | Eager (ms) | Default (ms) | ReduceOverhead (ms) | Best measured speedup |
|---:|---:|---:|---:|---:|
| 1 | 0.5862 | 0.2776 | 0.2439 | 2.40× |
| 8 | 0.9465 | 0.7809 | 0.7667 | 1.23× |
| 32 | 2.7243 | 2.0744 | 2.0712 | 1.32× |

The fastest Batch=1 run (ReduceOverhead) is 0.2439 ms vs Eager 0.5862 ms.
This is an observed association of compile mode and latency, not a measured
decomposition into time saved by fusion, graph replay, or dispatch.

## Numerical observations

- Compiled max abs error: 0.003906 at all batches.
- Compiled P99 abs error: 0.001953 at all batches.
- Compiled mean abs error: 0.000621 (B1), 0.000586 (B8), 0.000638 (B32).
- Maximum clamped-relative diagnostic increases with batch size:
  0.057913 (B1), 0.714302 (B8), 1.190186 (B32).
- At B32, reference=-0.000153, candidate=-0.001343, absolute difference=0.001190.
  With the 0.001 denominator floor, the relative diagnostic is about 119%, not
  evidence of a 119% classification error.
- Both compiled modes are allclose to eager using the exploratory tolerances;
  this does not establish downstream classification accuracy or bitwise identity.
- More elements are compared in larger batches, making extreme-value statistics
  such as max-relative-error more likely to be large.

## Limitations and next questions

- No model weights; cannot assess ImageNet task accuracy.
- No profiling trace yet; cannot apportion speedup to Kernel Fusion vs graph replay
  or CPU overhead. The later trace run will be a separate reproducible measurement.
- No confidence interval or multi-session statistics; a single timed run is a
  preliminary observation.
- The new scripted measurement protocol may return different timings. Keep the
  original baseline intact rather than overwrite it.
